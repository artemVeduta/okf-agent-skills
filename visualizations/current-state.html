1. Example OKF documents the suite will generate

OKF v0.2 conformance is exactly three bundle tests OKF spec (§11): every non-reserved .md file has a parseable YAML frontmatter block; every such block has a non-empty type; and index.md / log.md, when present, follow §8 and §9. Everything else in the frontmatter is optional. The documents below use the optional families because the suite chooses to, not because the format demands it.

All three are properties of a bundle, and §11 names no actor — there is no "consumer MUST enforce type presence" rule anywhere in OKF. §11's larger half runs the other way: a consumer MUST NOT reject for unknown type values, unrecognized keys, missing optional families, broken cross-links or a missing index.md. A validator may report; it may not fail a bundle on a producer obligation.

3.2 Non-parity, stated plainly

CORRECTED 2026-08-01 — the OpenCode non-parity claim was wrong. #17 concluded "no per-skill explicit invocation, no disable-model-invocation equivalent". Source verification at commit 32f278b refutes both halves:
  • OpenCode registers EVERY discovered skill as a slash command, automatically (packages/opencode/src/command/index.ts:134-152, a loop over skill.all() with no filter). Landed 2026-01-31 in v1.1.48 — six months before the note that missed it. No authoring step; a same-named config command or MCP prompt wins the name. Undocumented, but tested (ACP available_commands_update) and live in the TUI, the desktop app and POST /session/:id/command. /skills is the picker, not the only door.
  • Explicit-invocation-only IS achievable, two ways, because the model-facing catalog and the command registry are built from different filters: omit description — the skill is filtered out of <available_skills> (description !== undefined in both catalog renderers) yet stays registered as a command; or deny the skill permission, per skill (permission: { skill: { name: "deny" } }) or blanket (tools: { skill: false }), which strips the catalog while every skill remains reachable by slash.
  • Commands are prompt-injected, not a skill tool call (session/prompt.ts) — the template is the skill body, submitted as the user prompt. So the skill tool is never called and its permission.assert({ action: "skill" }) gate is bypassed on the slash path. That gate cannot be relied on for anything.
consequence #35's OpenCode adapter design — the marker-gated prompt-time transform — was chosen against the false constraint that OpenCode offers no explicit per-skill entry point. Pending amendment. Two research notes (opencode-skills.md, opencode-disable-model-invocation.md) carry the retracted claims. Caveats that stand: the description-omission lever rests on undocumented behaviour (the docs call the field required), permission-deny leaving the command alive is inferred intent, and no binary was run — every claim is source-read. docs/research/ecosystem-deep/opencode-commands-and-skill-invocation.md
Codex hooks cannot be scoped to a skill. Codex hooks have configuration scopes — user, trusted project, plugin — but no activation scope. No event input field or matcher exposes an active skill name. Per-skill lifecycle behavior must come from deterministic in-skill steps or a broader project hook whose scope is acceptable. adopted answer: no #16 Can Codex hooks be scoped to specific skills?

4. Retrieval — index navigation replaces the budget-aware runtime

SUPERSEDED 2026-08-01 — the whole budget-aware retrieval design is out of v0.1.0. #36 Replace budget-aware retrieval with index navigation OPEN supersedes #13, #28, #32 and #33 entirely. Gone: the budget-aware runtime, both ledgers, the LINE/CARD/SECTION/FULL tiers, the BUDGET→PIN→DISCOVER→RANK→ALLOCATE→NOTICE→VERIFY pipeline, the five omission codes, context reserves, retrieval receipts, the tokenizer and the cost model. The ticket is open and the replacement is not adopted — 4.1–4.3 below are the direction, not a decision. 4.5 keeps the superseded model on the record, because a reader of #8 will meet its evidence and must know it existed and why it went.
Impact analysis: docs/retrieval-simplification-impact.md.

4.1 The proposed replacement — the skill teaches the layout, the agent does the reading proposed

okf-read performs no retrieval of its own. There is no selector, no runtime call, no materialization step. The skill body teaches the bundle layout and the agent navigates it with the tools its harness already gives it — Read, Grep, Glob. Three-tier lazy loading, minus every ledger, tier, reserve, receipt and omission code. 

  HOP 1  okf/index.md                    bundle root — every type group, every subdirectory,
     │                                  each entry carrying the linked concept's description (§8)
     │       enough to answer "does this bundle know about X, and where would it live"
     ▼

     │
     ▼
  HOP 3  okf/<subdir>/<concept>.md       the concept body, read whole

  Grep is the escape hatch for body-only words, exactly as the agent would use it
  on any other repository. §8 indexes are the accelerator they were always described as.

  NOT a budget · NOT a ledger · NOT a tier ladder · NOT a receipt · NOT an omission code
An in-skill matcher was explicitly rejected. It reimplements grep without a tokenizer, and it reintroduces the exact defect that killed the budget model: an invented constant standing in for a measurement nobody can take. The agent's native tools are already the matcher.

4.2 Why the budget model went

No harness gives a skill a tokenizer. That single fact — established by #28 — means every token figure in the design was always characters divided by an invented constant. Building a safety guarantee on an invented constant is worse than not claiming the guarantee.
It dissolves two blocking findings outright. Uncalibrated deployment refuses every read — the rule "unknown budget with no calibrated fallback returns insufficient", which today makes #11's unconditionally-allowed A/A/A read row false in practice — is deleted with the sentence that caused it. No calibration corpus and no ticket to build one largely goes with it.
It resolves the statelessness contradiction by deletion. Profile quarantine was durable cross-call state in a runtime declared stateless, with nowhere in retrieve's signature to live. Deleting the cost model deletes the contradiction rather than negotiating it.
The price, stated honestly. Retrieval loses its only mechanically verifiable property — "never exceeds the allowance" is an assertion a fixture can check and #28/#33 checked it ~170,000 times; "did it return the right concept" is a judgement. And budget-awareness was the only mechanism in the specification that made "you are not seeing everything" observable. Deleting it is fine. Deleting it without a replacement disclosure rule is the one move that makes the product quietly worse rather than simply smaller.

4.4 What survives the supersession — carry it into #36

Query normalization in full — preserve the original query; NFC and case folding; retain one-character terms, digits, quoted phrases, paths and identifiers; add identifier subterms without replacing the original. No stopword deletion, no minimum term length, no substring stems, no implicit stemming, no generated synonyms. #33 called it "the cleanest part of the resolution"; it needs no calibration.
Statelessness and the no-memory rule — assume nothing returned earlier survives compaction or a source change. The one budget-era rule that must outlive the accounting that motivated it.
Exact references are demands — resolved first, never silently dropped, refused loudly with a quantified shortfall. The tier degradation ladder dies; the never-drop rule is free to keep.
Retrieval scope — deterministic exact-reference, source/path, index, frontmatter and lexical body retrieval only; semantic retrieval deferred; no importance/priority for v0.1.0; indexes are structural accelerators and curated maps are non-binding hints that neither hide unlisted concepts nor force linked ones into context.
Deprecated-concept exclusion (#14) — and it gets cheaper: reading the concept means frontmatter is present, so status filtering is always affordable and the "if status was not observed" branch becomes unreachable.
Untouched entirely — provenance and freshness (#12), identity and routing (#22), admission (#27), the guard (#29, #31), the trust matrix (#11 — zero budget coupling), restructuring, migration and the recovery contracts.
The superseded evidence is a hazard, and it is the largest one in the repository. #28 (45 cases, 4,312-run sweep, 30,000-run fuzz) and #33 (102 cases, 136,080-run sweep, two independent reviews) are the most detailed and most rigorously validated documents here — and they are now precise, executable, internally consistent, superseded policy sitting directly in the path of whoever writes #8. 5. Saving to docs — the write path

5.1 What counts as an evidence-backed update

An evidence-backed update is a bounded change to durable context with authoritative evidence, clear ownership and post-write validation — and it does not alter trust, status, freshness or review baselines. The lifecycle chooses one of four outcomes at each evidence checkpoint adopted (#6):

Abstain / no-op when the information is recoverable from authoritative artifacts, transient, speculative, duplicated, semantically unchanged, outside owner scope, or unsupported by evidence.
Originate only when durable reusable knowledge is missing, ownership is known and evidence supports a bounded concept. The result is draft and unverified.
Revise only when meaning or provenance-bearing metadata materially changes, the concept is owned and evidence supports the revision.
Every automatic update requires task intent, authoritative or explicitly adopted evidence, clear concept mapping, no unresolved conflict or unavailable dependency, bounded scope and post-write validation. "Small" means structurally bounded, not a numeric threshold.
The gate on content itself is the Pocock test proposed — "can the agent recover this from code alone? If yes, don't write it." The detection algorithm behind it (identifier density > 60% of paragraphs, rationale-signal ratio > 0.3, > 50% of links pointing at source code) is research-side with candidate thresholds needing fixtures; none of those numbers is adopted.
Source change is review evidence, not proof of staleness adopted. Provenance (sources) and review dependencies are different things: a sources[].resource identifies supporting evidence and does not by itself declare that a change makes the concept stale. Observation outcomes stay distinct and must not be collapsed: unchanged · changed · unavailable (a positively established existence failure) · unobservable (access, network, workspace, tool or resource limits). A concept with no review dependencies is not configured — not clean and not stale — and is quiet by default. #12

5.4 Guard state machine adopted

  idle ──> requested ──> previewed ──> confirmed ──> executing ──> completed
                                                                 ↘ failed

        any of the above ──(expiry)──> stale ──(re-preview)──> previewed
        any of the above ──(cancel)──> idle

  One manual-only operation in flight at a time.
  `previewed` is reachable without a request (a preview is read-only); `confirmed` is not.
  A request occurrence records and binds {operation, selector} to confirmable preview tokens;
  an unmatched preview stays read-only and can never confirm.

REFUSE — the ask does not match authorized work

NO_EXPLICIT_REQUEST   SELF_CONFIRMED
NO_PREVIEW            NOT_CONFIRMED
UNKNOWN_TOKEN         OPERATION_MISMATCH
SELECTOR_MISMATCH     PREVIEW_INCOMPLETE
PREVIEW_FAILED        EMPTY_SCOPE
TOKEN_SPENT           MUST_RESTART

EXPIRE — the ask matches, but what it was confirmed against has moved

SCOPE_MOVED
TRANSFORM_CHANGED
SUPERSEDED_BY_ANOTHER_RUN
CONFIRMATION_AGED_OUT
SESSION_BOUNDARY
The binding is --force-with-lease, not a counter. A confirmation binds to a fingerprint over {operation, selector, transformVersion, sorted [path, contentHash, plannedAction, riskClass]}, taken from the plan the human actually saw and re-verified at execute time against a freshly observed plan. mtime and size are excluded — a touch must not expire a confirmation, or humans learn to reconfirm blindly. Planned action and risk class are included — an edit turning a MOVE into a DELETE invalidates the confirmation even with an unchanged file set.
A completed run bumps a bundle epoch, obsoleting every outstanding sibling confirmation, and a spent fingerprint can never authorize a second run — so a rollback restoring a byte-identical corpus does not resurrect the token.

5.5 Where the guard state lives, and how sessions coordinate adopted

  In a Git repository:
    <git-common-dir>/okf-agent-skills/guard/<bundle-key>/
    linked worktrees therefore coordinate for the same logical bundle and
    conservatively invalidate one another even when their content differs

  In a non-repository workspace:
    <workspace-root>/.okf-agent-skills/guard/<bundle-key>/

  NEVER COMMITTED. A fresh clone, replacement instance or CI checkout inherits no
  confirmations, no epoch, no replay history, and cannot execute a token issued elsewhere.

  Execution protocol — four steps, execution holds an EXCLUSIVE lock for its full duration
    1. acquire the lock; reread the authoritative ledger; reject a mismatched generation,
       obsolete epoch, absent or spent token, or operation/selector mismatch
    2. recompute and validate the COMPLETE current plan UNDER THE LOCK
    3. atomically record `in-flight` BEFORE beginning mutation
    4. on success: spend the occurrence-bound token, advance the epoch, invalidate all
       sibling confirmations, clear `in-flight`, release the lock

  Epoch checking WITHOUT this lock is insufficient — it cannot stop two already-armed
  sessions from beginning together.

  Crash (process gone, OS lock released, `in-flight` remains): outcome is unknown.
  Confirmation and execution stay BLOCKED. Explicit recovery reports the operation,
  token, fingerprint and start time, then advances the epoch, clears all outstanding
  confirmations, and records the interrupted token with `outcome: unknown`.
  Recovery neither assumes success nor performs rollback.

The ledger may store paths, actions, risk classes and content hashes — never source content. Files use owner-only permissions where supported and write-temp / flush / atomic-replace discipline. If the runtime cannot create, secure, lock or atomically replace the ledger, confirmation and execution fail closed. #31 Decide where manual-operation guard state persists and how concurrent sessions coordinate

5.6 Operation manifest and the recovery gate adopted

  OPERATION MANIFEST  — the durable record of ONE broad / destructive / identity-changing operation
    lives in a separate durable store OUTSIDE every mutation target AND outside the guard ledger
    survives repository replacement and the writing machine
    written completely -> flushed -> atomically replaced -> content-verified
    sealed at MANIFEST_DURABLE, immutable thereafter (it sits inside the approval fingerprint)
    later observations APPEND an OBSERVATION record; they never amend the manifest

    missing · torn · corrupt · truncated · unknown-schema  =>  indeterminate
    blocks execution and any recovery claim.  Never recover from a valid-looking prefix.

  EACH EFFECT   INTENT{undo} ──> mutate ──> OUTCOME     each durable IN THAT ORDER
    so death between the write and the journal append leaves a dangling INTENT that
    reconciliation can SEE, rather than an unrecorded mutation.
    observedHash = H(contentHash, verificationHash) is rechecked at EVERY INTENT —
    a concurrent VERIFICATION is as much a reason to abort as a concurrent edit.

  RECOVERY GATE  — passes only when ALL hold:
    ✓ independent content-addressed snapshot of affected bundles + relevant untracked files
    ✓ snapshot stored OUTSIDE the mutation target
    ✓ successful restore into a DISPOSABLE location
    ✓ restored-content hash verification
    ✓ OKF validation + operation-specific identity / link / provenance / trust checks
    ✓ documented rollback procedure
    ✓ snapshot and restore evidence BOUND to the approved preview
    ✓ post-operation validation

    Trust tier, confirmation, Git history, PR approval, reflogs, automatic commits and
    `git archive` cannot override or alone satisfy this gate.
    "An automatic git commit is not a backup" — the only proof a backup works is restoring
    it to a disposable location and verifying the files.

  TERMINALS  = settlement (applied | reverted | failed) × cleanliness (clean | dirty)
    which makes "succeeded but left residue" a NAMEABLE state.
    Effects rollback cannot reverse are recorded as residue; the result is `dirty` or
    `indeterminate`, never `clean`.
    rollback-failed is a LOUD TERMINAL. No automatic repair, no inverse retry.
    Repair starts as a NEW operation with a new preview, approval, snapshot and gate.
    Rollback ALWAYS requires fresh approval; parent approval is context only.
    The inverse manifest is built from what actually landed, not from what was planned.

5.7 Write-new-then-swap

The single convergent invariant. rsync's temp-file-and-rename, blue-green deployment's never-mutate-live, and restic's packs→index→snapshots ordering independently arrive at it: write new, then swap; never mutate in place. For migration this means a separate staging area, validation, then an atomic write-new-then-swap publication. Originals are never mutated, relocated or deleted by migration; cleanup, if ever needed, is a separate recovery-gated operation. #19, #23 Research safe migration of existing knowledge corpora into OKF 
  MIGRATION — a manual, explicitly requested okf-lifecycle operation

  request names ONE source root, ONE explicit project mode, and explicit include/exclude rules
  — it does NOT scan a workspace or discover sources implicitly
        │
        ▼
  DRY-RUN PREVIEW  complete only when EVERY selected input has a disposition
     manifest lists scope, mode, classifications, paths, transformations, links, provenance,
     residue, conflicts, attachments, retained originals, output identities, hashes,
     recovery evidence
     An incomplete preview CANNOT mint a confirmation, and completeness is FRESHLY
     RE-CHECKED at execution — not inferred from a sentinel.
        │
        ▼
  APPROVAL  binds to the explicit request AND the complete plan
        │
        ▼
  SNAPSHOT  independent · restored in a disposable location · checked BEFORE execution
     Git history, reflogs and `git archive` are not the sole recovery mechanism.
        │
        ▼
  EXECUTE  bundle-scoped operation lock · fresh source and target identity/content checks
     writes into a SEPARATE STAGING AREA · validation
     drift after preview ABORTS WITHOUT TARGET MUTATION and requires a new preview
        │
        ▼
  PUBLISH  atomic write-new-then-swap
     Incomplete work is NOT published. A partial run remains staged and reported until
     the user narrows the request or resolves the blocker.

  outcomes:  complete (every selected input has a safe disposition, including inert residue)
             partial  (selected work remains unresolved)
             failed | indeterminate  (recovery or post-operation uncertainty) — never success
Structural success is not semantic fidelity. Frontmatter parse-tree round trips, file counts, link handling and conformance checks do not establish that migrated content retains its intended user-authored meaning. A semantic-fidelity claim requires explicit human review of all conflicts and residue plus representative high-risk conversions. Without that evidence, semantic fidelity is not assessed — and the suite never emits a bare conformant, compliant or succeeded.
Every harness runs the same request, preview, confirmation, plan binding, execution checks and outcome semantics. Adapters may change presentation only. A harness that cannot attest a complete preview or an explicit confirmation blocks the operation rather than weakening it.
